# User Story Audit: git-dispatch

A workflow-by-workflow assessment of git-dispatch ergonomics. The goal is to identify what's good, what's painful, and where the next investment of effort would most reduce user friction.

This audit is **systematic** and complements the **session-specific** insights in `IMPROVEMENTS.md` and `hurdles-and-improvements.md`. It is grounded in:

- Real session evidence: `BUG-*.md`, `pitfall-*.md`, `REPORT-*.md`
- The command surface in `AGENTS.md`
- Direct workflow tracing through `git-dispatch.sh`
- Recent autonomous-agent sessions where dispatch was driven by Claude

## Executive summary

### What's working well (do not break)

1. **Single source of truth model.** The "edit on source, propagate to targets" mental model is unambiguous. Once internalised, users don't re-derive it - they just use it.
2. **Trailer auto-management.** `dispatch commit "msg" --target N` is the right level of abstraction. Users never write trailers by hand.
3. **Independent target branches.** Each target is its own PR with its own base. Reviewers don't see a stack. GitHub doesn't need a special UI.
4. **`checkout N` semantics for integration testing.** The "ephemeral integration view" idea is exactly what testing 1..N together needs.
5. **Status output.** Clear column-aligned summary. Merged / in-sync / behind / DIVERGED states are immediately legible.
6. **The `--source-keep` escape hatch.** Concise, well-named, solves the regen file problem cleanly when it works.

### Top friction (in priority order)

1. **`all`-trailer footgun keeps re-firing after merges.** Same conflict, same resolution, every apply. Spec proposed in `SPEC-auto-resolve-all-trailer-post-merge.md`.
2. **No commit-time validation of trailers vs. file ownership.** Mis-tagged commits silently land and bite later. `git dispatch lint` exists but requires opt-in `.git-dispatch-targets` config.
3. **Force-push trap after source rebase.** The `apply reset` cascade rewrites target history requiring `--force`, which breaks open PRs' review threads. Documented in `pitfall-apply-reset-force-push-trap.md`.
4. **Sync ergonomics during conflicts.** `sync --resolve` leaves the user in a worktree path the rest of the dispatch CLI can't address. They `cd` there, run `git -C ...` for everything, copy-paste paths. Documented in `REPORT-sync-conflict-ergonomics-for-claude.md`.
5. **No pre-push verification.** Apply produces a target branch whose first feedback is CI 5-10 minutes later. Documented in `IMPROVEMENTS.md` section "Pre-push Verification".
6. **`checkout source` switches branch but doesn't release dispatch state.** Sync after returning to source still complains about active checkout until `checkout clear` runs explicitly.
7. **`retarget` cannot move FROM `all`.** Hardcoded refusal even though that's the most useful direction for fixing mis-tagged shared commits.
8. **Recovery commands feel like manual git.** `git dispatch continue` after a conflict tells the user to `git -C <wt> cherry-pick --continue` - a layering leak that requires knowing both git and dispatch.

### Top recommendations

In order of impact-per-effort:

| # | Change | Impact | Effort |
|---|--------|--------|--------|
| 1 | Implement `SPEC-auto-resolve-all-trailer-post-merge.md` | High (kills #1) | Medium |
| 2 | Allow `retarget --commit X --to-target N` to move FROM `all` | High (kills #7, partially mitigates #1) | Low |
| 3 | Add a default `.git-dispatch-targets` template generated by `init` | Medium (improves #2) | Low |
| 4 | Make `checkout source` auto-clear when no unpicked checkout commits exist | Medium (kills #6) | Low |
| 5 | Add `dispatch verify <N>` for local target build/test before push | Medium-High (kills #5) | Medium |
| 6 | Move sync conflict resolution into the dispatch CLI directly | Medium (kills #4) | Medium |
| 7 | Surface audit log + skip reasons inline in `apply` output | Low (compounds #1) | Low |

## Personas

### P1: Solo developer using stacked PRs

The original target user. Has 3-5 logical changes, doesn't want them in one mega-PR or in awkwardly stacked dependent PRs. Wants each as its own reviewable unit.

**Daily flow:** edit -> commit -> apply -> push. Occasional checkout for integration tests. Reviews + iterates per target.

**Pain delta vs. plain git:** lower (dispatch reduces effort). vs. `ghstack`: lower friction because each target is independent.

### P2: Multi-developer team where one PR depends on another

Teams where T-2 (FE) is built on T-1 (BE). Want T-1 reviewable independently while T-2 work continues.

**Daily flow:** same as P1, plus coordination on when targets get merged. Post-merge sync is a regular event.

**Pain delta vs. plain git:** medium (the post-merge `all` footgun bites them disproportionately - they hit merges often).

### P3: Autonomous agent (Claude / Codex / similar)

Agents driving dispatch via the skill prompt. No long-term memory across sessions. Can't internalise unwritten conventions.

**Daily flow:** read SKILL.md, run commands, react to errors. Heavily relies on error messages and command output to know what to do next.

**Pain delta vs. plain git:** higher than humans (agents have less context to fall back on; ambiguous errors stall them).

### P4: Reviewer / manager

Doesn't run dispatch. Sees the targets as PRs in GitHub.

**Pain delta vs. plain git:** zero. Targets look like normal PRs. (This is the design's biggest win.)

## Workflow inventory

For each workflow: trigger, key steps, current friction, what works well, recommended improvement.

### W1. First-time setup

**Trigger:** New project / new source branch needs dispatch.

**Steps:**
1. `git dispatch init` (interactive prompts for base + target pattern)
2. First `dispatch commit "..." --target 1`
3. First `dispatch apply` to create targets
4. First `dispatch push <N>` per target

**Friction:**
- No template `.git-dispatch-targets` is generated. User has to know that file exists, then write the globs from scratch.
- `init` doesn't surface the relationship between target pattern and PR branch naming convention (e.g., team prefix, ticket IDs). User picks something then later regrets it (and uses `alias` to rename).
- `init` doesn't suggest or warn about merge-strategy implications (squash-merge vs. rebase-merge; only squash is properly handled).

**What works:** Interactive prompts are clear. Defaults are sensible.

**Recommendation:** `init` should generate a stub `.git-dispatch-targets` with one comment-line per detected top-level monorepo dir + a `# shared:` line. User edits it. Alternative: a `dispatch lint --suggest` mode that proposes a config based on observed commit history.

### W2. Daily commit -> apply -> push

**Trigger:** Made a change, want it on the target PR.

**Steps:**
1. Edit files on source.
2. `git dispatch commit "msg" --target N`
3. `git dispatch apply N`
4. `git dispatch push N`

**Friction:**
- After `apply N`, no local sanity check (compile, lint, test) before `push`. CI failure is the first feedback.
- `apply N` output doesn't show which commits were applied to which target - just a summary. Hard to diff against status without re-running `status`.
- `push N` doesn't auto-create the PR; user must run `gh pr create` separately and manually pick the base branch.

**What works:** Single command per step. No trailer hand-editing. Fast-forward push when source is in sync.

**Recommendation:** Add `dispatch verify N` (run target's package's test/lint/type-check before push). Add `dispatch push N --pr` to chain `gh pr create` with the correct base.

### W3. Sync with master

**Trigger:** Master moved forward. Source needs the changes; targets need them too.

**Steps:**
1. `git dispatch sync`
2. If conflict: `--resolve`, fix in worktree, `git dispatch continue`.

**Friction:**
- Sync conflict drops the user into a worktree path they can't address from the main shell except via `git -C <path> ...` + copy-paste. Painful for both humans and agents.
- Sync output doesn't surface which targets had auto-resolutions (e.g., Source-Keep applied) vs. clean fast-forwards. User can't tell what happened.
- Sync followed by `apply N` is a common sequence but isn't a single command.

**What works:** Idempotent. Handles `--all` for merged targets correctly. Skips merged targets by default.

**Recommendation:** Implement the conflict-in-CLI redesign from `REPORT-sync-conflict-ergonomics-for-claude.md`. Add `dispatch update <N>` as a sync+apply combo.

### W4. Integration testing via checkout

**Trigger:** Need to test targets 1..N together.

**Steps:**
1. `git dispatch checkout N`
2. Run tests, manual smoke, etc.
3. `git dispatch checkout source` to return
4. `git dispatch checkout clear` to delete the throwaway branch

**Friction:**
- Step 4 is required even after step 3. Easy to forget. Subsequent `sync` aborts with a confusing message.
- `checkout N` rebuilds the integration branch each time even if the underlying targets haven't changed. Slow when there are many commits or large diffs.
- No way to test target N + target 4 together (skipping 2 and 3) - the cumulative model is rigid.

**What works:** Clean isolation; unrelated to source's state. Branch name encodes target ID for self-documentation.

**Recommendation:** Auto-clear on `checkout source` when no unpicked checkout commits exist. Cache the integration branch SHA and skip rebuild if inputs haven't changed. Allow `checkout 2,4` for non-contiguous integration views.

### W5. Bug-fix on a checkout (the loop)

**Trigger:** Found an issue while integration-testing.

**Steps:**
1. On checkout branch: edit + `git dispatch commit "fix"` (auto-detects target from branch name).
2. `git dispatch checkin` (cherry-picks fixes back to source).
3. `git dispatch checkout source`.
4. `git dispatch apply N`.
5. `git dispatch checkout clear`.

**Friction:**
- 5 commands for 1 logical action ("apply this fix to target N").
- If the fix touches a generated file, user must remember `--source-keep`. No reminder, no detection.
- If `apply N` then conflicts on an unrelated `all`-trailer commit (the footgun), the user is now wrestling with a problem they didn't cause.

**What works:** Auto-detection of target from checkout branch is excellent. No trailer hand-management.

**Recommendation:** Single `dispatch checkout-fix N` that wraps steps 2-5 into one command. Auto-detect generated files via `.gitattributes` or path globs and apply `--source-keep` automatically with a notice.

### W6. Generated files (OpenAPI, protobuf)

**Trigger:** Backend schema changed; OpenAPI client needs regen for FE target to compile.

**Steps:**
1. On source: `pnpm openapi`.
2. `git dispatch commit "regen" --target all --source-keep`.
3. `git dispatch apply`.

**Friction:**
- `--target all` is the dangerous option (post-merge footgun risk). Better in this case is `--target N` for the target whose schema changed, but then the FE target won't have the regenerated types until that target is merged.
- `--source-keep` is the right tool but only works if regenerated files are stable across targets. If two targets need different regens, `--source-keep` silently overwrites.

**What works:** When it works, it works in one trailer. The keyword `--source-keep` is memorable.

**Recommendation:** Allow `--target 1,2,3` (multi-numeric) instead of `all` for cases where a commit applies to a known subset. This avoids the post-merge footgun for genuinely shared regen. Document the decision tree clearly: "regen for one target's schema -> tag that target only; regen for shared-utility schema -> `all` + `--source-keep`."

### W7. Post-merge sync

**Trigger:** A target's PR merged. Other targets are still open.

**Steps:** See `REPORT-post-merge-agent-recipe.md`. Roughly: `status` -> `sync` -> `lint` -> `apply N` -> resolve all-trailer footgun manually -> `push N`.

**Friction:** Maximum. This is the single highest-friction workflow. Every recurrent user hits this multiple times.

**What works:** Status output flags the post-merge condition with a banner. Sync correctly skips merged targets.

**Recommendation:** SPEC for auto-resolution (top recommendation). Plus the lint-with-ownership-config to catch mis-tags before they merge.

### W8. Review feedback iteration

**Trigger:** Reviewer comment on PR for target N. Need to push a fix.

**Steps:**
1. Edit on source.
2. `git dispatch commit "Address review" --target N`
3. `git dispatch apply N`
4. `git dispatch push N`

**Friction:** Same as W2. Plus: if multiple targets need synced changes after review, no batch command exists.

**What works:** Trailer auto-management means the new commit threads correctly. Apply is fast-forward.

**Recommendation:** None specific. Improvements to W2 cover this.

### W9. Force-push recovery (`apply reset`)

**Trigger:** Source rebased; targets are now stale. Or the all-trailer footgun forced you here.

**Steps:**
1. `git dispatch apply reset N` (or `apply reset all`).
2. `git dispatch push N --force` (for each).

**Friction:** EVERY consumer of the target's PR loses their review threads' line anchors. Reviewers complain. Sometimes the PR loses its CI history for the green check.

**What works:** Idempotent. Recovers from any stale state. The `--force` requirement is a deliberate friction point that makes sure the user knows what they're doing.

**Recommendation:** Make this rare. Most uses of `apply reset` today are workarounds for the all-trailer footgun. Fixing that (SPEC) reduces the frequency. Document the PR-thread-loss cost so users avoid it more deliberately.

### W10. Multi-tenant cleanup

**Trigger:** Some targets merged; clean up local state.

**Steps:**
1. `git dispatch status` to confirm what's merged.
2. `git dispatch delete <N>` per target, or `git dispatch delete --prune` for all merged.

**Friction:** Cosmetic. Some users accumulate dozens of merged targets and `--prune` doesn't suggest itself.

**What works:** `--prune` exists. `delete --dry-run` previews. `--yes` for scripting.

**Recommendation:** `status` output could end with "Tip: run `dispatch delete --prune` to clean up 5 merged targets" when applicable.

### W11. Naming and aliases

**Trigger:** Need a target branch to follow team naming conventions (`team/feat/Ticket-1234`).

**Steps:**
1. `git dispatch alias N team/feat/Ticket-1234`

**Friction:** Per-target. If you have 10 targets, you alias 10 times. `init`'s `--target-pattern` handles the simple case but not custom per-target.

**What works:** Aliases survive `apply reset`. `delete` and `reset` clear them.

**Recommendation:** `dispatch alias --bulk` reading a file or stdin with `<N> <branch-name>` per line.

### W12. Diagnose divergence

**Trigger:** Status reports `(DIVERGED)` for a target.

**Steps:**
1. `git dispatch status` shows the flag.
2. User figures out why.
3. `checkout N` -> reconcile -> `checkin` -> `apply N` -> `push N`.

**Friction:** Step 2 is hard. The DIVERGED flag is the only signal; the user must investigate manually.

**What works:** The flag is reliable. Cosmetic vs. real divergence are correctly distinguished.

**Recommendation:** `status --explain N` that walks the divergence chain: "target 2 has commit X (subject: '...') with no traceable source commit. Suspect: someone pushed directly to target 2."

## Cross-cutting issues

### CC1. Mental model leakage

Many error messages tell the user to run raw git commands inside a temp worktree path. This breaks the "source/target/checkout" mental model. The user has to context-switch into "raw git in this weird worktree" to make progress.

**Examples:**
- Sync conflict: "Resolve in: /var/folders/.../wt-XXXX. Then run: git -C /var/folders/.../wt-XXXX cherry-pick --continue"
- Apply conflict: same pattern.
- Auto-stash messages reference `git stash list` not `git dispatch ...`.

**Fix:** Internalise these into the dispatch CLI. `git dispatch resolve <file>` to mark a file resolved (using `--ours`, `--theirs`, or staged). `git dispatch continue` should be the only post-conflict command users ever need.

### CC2. State sprawl

`.git/dispatch-*` (multiple files), per-source git config keys, target branches, target alias config keys, checkout branch tracking, audit log (proposed). Users can't easily inspect "everything dispatch knows".

**Fix:** `dispatch state --show` that dumps all relevant config keys + tracked branches in one block. Useful for debugging weird states.

### CC3. Conventions only documented in skill prompt

Some constraints (e.g., "Use `dispatch commit` not raw `git commit`") are in `AGENTS.md` but not in `README.md` or in command help. Users not running through Claude miss them.

**Fix:** Move constraints into `README.md`'s "Common pitfalls" section. Add per-command help text via `--help` to all commands.

### CC4. Versioning and migration

No dispatch-version field anywhere. If the tool's config schema changes (e.g., the proposed `dispatchautoresolveall` key), old repos silently use the old schema.

**Fix:** Track a version in `branch.<source>.dispatchversion`. On startup, compare to the binary's version. If older, migrate (with backup).

## Priority ranking

For "make this tool as easy to use as possible" the order I'd implement:

1. **SPEC: auto-resolve `all`-trailer post-merge.** Kills the highest-frequency frustration with one focused change.
2. **Allow `retarget` to move FROM `all`.** Two-line change; opens the right escape hatch for mis-tagged commits.
3. **Auto-clear checkout on `checkout source`** (when safe). Removes a confusing dispatch-state-vs-git-branch mismatch.
4. **`init` generates a `.git-dispatch-targets` template.** Makes `lint` opt-in by default rather than buried.
5. **`dispatch verify <N>`.** Pre-push compile/test/lint to cut the CI feedback loop.
6. **Sync conflict ergonomics** (CC1 fix for sync specifically).
7. **`dispatch checkout-fix N`** as a single-command wrapper for the bug-fix-on-checkout loop.
8. **Audit log + status footer** (covered by the SPEC; calling it out for visibility).
9. **`status --explain N`** for divergence diagnosis.
10. **Versioning + migration** for safe schema evolution.

Items 1-4 alone would account for the majority of friction in the workflows audited above. Items 5-7 round out the daily-use cases. Items 8-10 are quality-of-life on top.

## How to use this audit

- **Implementer:** pick from the priority ranking. Each top-10 item maps to a workflow above with concrete steps.
- **Reviewer:** check whether your proposed change addresses one of the listed frictions or introduces a new one.
- **Future agent:** when you encounter a friction not listed here, append a new W## or CC## entry rather than editing existing ones. Keep the audit append-only.

## Out of scope for this audit

- Performance (apply latency, sync time on large repos). Untracked currently; would need profiling.
- Cross-repo / submodule support. Not modeled in the current design.
- Web UI / GitHub integration. Pure CLI today.
- Migration from `ghstack` or `spr` to `git-dispatch`. Worth a separate doc.
